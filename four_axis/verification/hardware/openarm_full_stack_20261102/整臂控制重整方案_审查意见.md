# 整臂控制重整方案 · 逻辑审查意见

审查对象：`verification/hardware/openarm_full_stack_20261102/整臂控制重整方案.md`（2026-11-02）
审查方式：静态源码核对；未改生产代码、未接实机、未编译 ROS、未打开串口。

## 结论

**方向正确，主线 A→B→C→D 正确，DMMC02 不是 SocketCAN、反馈 ID0、KDL 自身是 bus owner、4 轴/J5、4DOF 这些判断都对。** 但方案目前仍停留在“架构正确”，有三处会直接让 A/B 做出来“看起来通了、实际方向/模型错”的阻断，必须先定死再进入硬件接口实现。

## 阻断 1：J1 的 sign/zero/限位仍是多套事实源

这是“方向错了”的真正残留，不是再加一个 +1 能解决的。

| 来源 | J1 范围 | 说明 |
|---|---|---|
| `src/slaihand_description/urdf/slaihand_four_axis.urdf:46` | **−80°～+200°**（−1.3963～3.4907 rad） | 轴 `0 0 -1`；与用户实测扇区一致 |
| `src/slaihand_description/urdf/slaihand_five_axis.urdf:28` | **−80°～+200°** | 轴 `0 0 -1` |
| `slai_console/core.py:15` | **−200°～+80°** | 当前五轴/旧工具用的镜像范围 |
| `verification/hardware/five_axis_20261102/five_axis_config.json` | **−198°～+78°** | 当前五轴 J1 行程 |
| `outputs/标定记录_20261102/修正_J1方向_20261102.*` | **−200°～+80°** | 我之前按“镜像旧模型”写的修正 |

矛盾点：

- 用户实测 J1 物理正方向 = 编码器增大；`hardware_sign=+1`、zero 不变后，**模型角就是物理角**，范围应是 **−80°～+200°**。
- `core.py` / `five_axis_config` / 修正记录里的 **−200°～+80°** 是旧 sign=−1 模型的镜像，不是现在的物理扇区。
- 新 ROS 若按 URDF 建，J1 是 **−80°～+200°**；旧 UI/单轴工具仍按 **−200°～+80°**，两个入口会再次各自解释。方案第 14 行已提到“旧方向表、模型扇区、用户实测扇区有差异”，但没有给出**以哪个为准、何时删除旧值**。

**必须先做（建议作为第 0 步，不是 A 的一部分）：**

1. 定死唯一来源：**URDF/`hardware_mapping` 的 J1 = sign +1、zero 不变、范围 −80°～+200°**。
2. 删除或标记废弃：`core.py` J1 −200..80、`five_axis_config` J1 −198..78、旧修正记录里的 J1 范围。
3. J4 也要一起核对：URDF J4 `−90°～+50°`、`hardware_sign=−1`；J3 `±90°`，J3 的 180° 只是模型摆放，不要混进零位/sign。J5 仍不进入控制集合。
4. A 的验收里加一条：**已知方向/已知限位的单轴原始帧回放**，不是只看“q 与报文一致”。否则 A 会通过，B 的第一条轨迹仍可能反。

## 阻断 2：四轴 URDF 和五轴 URDF 不是同一个模型

方案说“已有四轴描述”，但仓库里两套 URDF 的 J2/J3/J4 不一致：

| 关节 | 四轴 URDF | 五轴 URDF |
|---|---|---|
| J2 轴 | `0 0 1` | `0 0 -1` |
| J3 原点 | `0.0797365 −0.000108 −0.0365` | `−0.0552387 0.0575252 −0.0362749` |
| J4 原点 | `0.04125 0 0.1395` | `0.0016622 0.0864890 0.2745533` |
| J5 | 无 | `continuous`，identity 占位，非真实安装位置 |

如果按“四轴 URDF”接 KDL/MoveIt，J2 方向会反、J3/J4 连杆长度/安装位置会错；重力补偿和末端规划都会建立错模型。**必须先确认哪套是实机**（从 J3/J4 尺寸看，五轴那套更像实机，四轴可能是旧的简化模型），然后：

- 只保留一套实机 URDF；
- J5 在实机模型中固定/排除，不用 continuous 占位参与 KDL/MoveIt；
- J2 轴方向、J3/J4 原点与实测/CAD 对齐；
- KDL 参数、MoveIt SRDF、碰撞模型都从这同一套派生。

否则 C 的重力补偿会“数学对、模型错”，比不做更危险。

## 阻断 3：Windows UI + WSL ROS + DMMC02 的 owner 没有落地

方案写“现有 Windows 界面作为上层操作端”“物理串口只由硬件 owner 持有”，但没回答：

- DMMC02 USB 到底接 Windows 还是 WSL？接 WSL 后 Windows 就没有 COM9，旧 UI 不能再用；接 Windows 则 ROS 在 WSL 里拿不到 `/dev/ttyUSB`。
- Windows UI 和 WSL ROS 之间用什么 API？ROS 2 DDS 跨 WSL/Windows 的发现、防火墙、QoS、延迟没有定义；这不是“UI 发个关节目标”一句话。
- 旧 `native_mit_console`、`five_axis_console`、`auto_load_console` 仍能自己开 COM9；方案只说“降为诊断”，没有 **OS 级/进程级 owner 锁**。只要旧窗口还能开串口，“唯一 owner”就是约定，不是事实。

**建议先做决策，再写硬件接口：**

- 首选：**ROS + UI 都在 Ubuntu 原生**，DMMC02 只接 Ubuntu，一个 owner、一个 DDS 域；Windows 只做远程桌面/文档。
- 次选：WSL ROS + Windows UI，必须明确 DDS 桥、USB 只给 WSL、Windows 侧旧工具禁用或只读，并做 owner 互锁。
- 无论哪种，A 之前要有 **“谁持有串口”的硬门**（udev/usbipd/flock/单进程），不能靠 UI 文案。

## 其他逻辑问题

### B 的命令合成还没定义到可实现

方案说“位置目标 + 驱动PD + 重力前馈”，但没有一张**唯一责任表**：

- `JointTrajectoryController` 只发 `position`（当前 `slaihand_controllers.yaml` 就是 `command_interfaces: [position]`，`open_loop_control: false`）；
- 驱动侧 MIT 需要 `q, dq, Kp, Kd, tau_ff`；`Kp/Kd` 用 160/5，`dq` 用不用 JTC 的 velocity？
- KDL 的 `tau` 在**哪个进程、哪个周期**算？在硬件接口 `write()` 里同周期算，还是单独 controller 发 `effort`？方案图里 `G→CMD→HW` 没定。
- `q_model = sign*(raw-zero)`、`tau_motor = sign*tau_model`、`dq_motor = sign*dq_model`；J1 +1、J4 −1，这些必须在硬件接口一处完成。
- 当前 URDF `effort=1`、`velocity=0.5` 是假值；JTC 的 `state_interfaces` 只有 position/velocity，没有 effort。A 要“effort 与原始帧一致”，但接口里现在没有 effort，需要新增。
- 建议在 B 之前写一张表：`JTC position → q_target`；`JTC velocity → dq_ff（或 0）`；`Kp/Kd=160/5`；`tau_ff=KDL`；`MIT pack`；`TMAX/PMAX/VMAX`；`sign/zero`；`quantization`；`stop/FD`。谁算、谁限幅、谁唯一，写死。

### A 的验收缺时序/时效/模式

当前只要求“q/dq/effort 与原始帧一致、0 运动”。还需要：

- 持续 **周期、发送间隔、反馈延迟、丢帧、乱序** 的实测（方案 B 才提，但 A 就要知道 DMMC02 能不能撑 100Hz）；
- `mode==1`、`timeout==2000`、`state==0`、PMAX/VMAX/TMAX 的**启动时重读**；
- 反馈时效：只读工具 `MAX_AGE=1.0s`，控制链路不能用 1s；A 要定控制时效（例如 0.05s）和 stale 行为；
- 反馈 ID0 的分帧：现有 `verification/hardware/four_axis_monitor.py` 已经用 `data[0]&15` 分运动反馈、`can_id==regs[i][7]` 校验，并区分 `0x33` 寄存器回复；方案说“按 payload 轴号”是对的，但要把**帧类型→轴→字段→时间戳→未知帧拒绝**写成表，并做**原始帧回放**，否则 A 的 q 可能来自错轴。

### C 的重力补偿

方案对“不用仿真质量、不用积分偏置当重力、官方 KDL 自身是 bus owner”的判断是对的。补两点：

- KDL 链条必须用**实机 4 轴 + J5 固定**的那套 URDF/参数；官方 7 轴惯性参数不能直接搬；
- 参数辨识要有**可观测性检查 + 留出姿态验证**，并明确“补偿关闭/开启”的同姿态对比；不要用自动采集的局部点直接上线。

### D 的末端与示教

- 4DOF 不能承诺任意 6D，方案已写清楚；
- “示教”要区分 **记录/回放** 和 **零重力拖动示教**：前者 A/B 后即可做，后者依赖 C 的重力补偿和安全扭矩限制；方案矩阵里已提醒“不把能记录写成拖动示教回放完成”，建议在 D 的验收里也分开。

## 建议顺序（修正版）

0. **冻结模型/符号/限位单一事实源**：J1 −80..+200、J4 −90..+50、J3 ±90、J5 固定；选四轴还是五轴 URDF；删除旧 `core`/五轴配置里的 J1 −200..80；旧单轴工具标记诊断。
1. **A：真实状态链路**：DMMC02 分帧/ID0 路由 + ros2_control 真实状态接口 + 单 owner + UI/ROS 主机决策；只读、0 运动、0 参数写；加时序/时效/模式/effort。
2. **B：四轴协调**：按唯一责任表接 JTC + 驱动 PD + KDL tau；先一条四轴小轨迹，验证方向、到达、取消、异常停止。
3. **C：重力补偿**：实机 4 轴 + J5 固定模型、参数辨识、留出验证、开关对比。
4. **D：末端与示教**：4DOF MoveIt；先记录/回放，再讨论零重力拖动。

## 保留方案中正确的部分

- 以 ROS 2 / ros2_control 为主干，Windows UI 只做上层；
- DMMC02 不是 SocketCAN 配置名，保留串口帧、复用官方编解码；
- 反馈 ID0 必须分帧、按 payload 轴号；
- 官方 KDL 数学复用，但不让 gravity_compasation 和硬件接口同时当 bus owner；
- 4 轴、J5 不进入控制、4DOF 不承诺 6D；
- A→B→C→D 的里程碑和“fake 通过不等于实机通过”的边界。

这些都对。问题不在方向，而在**进入 A 之前没有把模型/符号/限位和 owner 定死**；这两件事不解决，A 会“状态看起来对”，B 会“轨迹走错”，C 会“重力模型错”。
