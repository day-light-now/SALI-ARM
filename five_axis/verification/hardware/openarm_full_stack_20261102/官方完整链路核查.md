# OpenArm 官方完整链路核查（2026-11-02）

范围：只读官方 enactic GitHub 源码与同仓 docs；未操作机械臂、串口或 UI，未编译运行官方控制器。以下“已实现”表示读到实际运行路径，不代表在本机验收。当前项目 J1–J4 可控；J5 虽已接线但方向、零位、模型未知，仍须从所有命令集合中排除。

## 结论

OpenArm 远不止 openarm_can：官方有真实 ros2_control 硬件插件、整臂轨迹接口、MoveIt2 规划配置、末端夹爪、独立的重力补偿/双向与单向遥操作，以及较新的 Dora 遥操作与数据采集链路。应复用其分层和已有组件，把当前 DMMC02 串口传输、4 轴映射和本机模型作为适配层；无需继续围绕单轴 MIT 脚本扩功能，也不应以购买新适配器为前置条件。官方代码不是本机即插即用的完整产品，尤其不能原样启动硬编码 7 轴并自动回零的硬件插件。

## 真实 ROS2 链路及具体边界

`MoveIt2/JointTrajectory action → JointTrajectoryController → position/velocity/effort command interfaces → OpenArmHW.write → MITParam{kp,kd,q,dq,tau} → openarm_can → SocketCAN → 电机`；反馈由 `refresh_all/recv_all → get_position/get_velocity/get_torque → state interfaces → joint_state_broadcaster`。依据：[OpenArmHW 实现](https://github.com/enactic/openarm_ros2/blob/8f23aeabb372c256f7807b9a74d48e035fc68386/openarm_hardware/src/openarm_simple_hardware.cpp)、[整臂控制器配置](https://github.com/enactic/openarm_ros2/blob/8f23aeabb372c256f7807b9a74d48e035fc68386/openarm_bringup/config/controllers/openarm_bimanual_controllers.yaml)、[MoveIt 控制器映射](https://github.com/enactic/openarm_ros2/blob/8f23aeabb372c256f7807b9a74d48e035fc68386/openarm_bimanual_moveit_config/config/openarm_v2.0/moveit_controllers.yaml)、[真实/mock 插件与增益注入](https://github.com/enactic/openarm_description/blob/10ca9bf2f49ef93a2f0f83f97ed2c0fb42dd9a90/assets/robot/openarm_v2.0/urdf/ros2_control/openarm.ros2_control.xacro)。

1. `kp1…kp7/kd1…kd7` 是硬件参数；本实现未导出动态 kp/kd command interface，也不是ROS PID控制器自动生成的增益。write把固定增益与3种命令共同装入MIT。ROS2默认轨迹配置只申请position，不能因为导出effort就宣称重力前馈已经接通。
2. `ARM_DOF=7`、默认型号 `[DM8009,DM8009,DM4340,DM4340,DM4310,DM4310,DM4310]`、send ID 1–7、recv 0x11–0x17、可选夹爪0x08/0x18 均硬编码。仅修改controller的joints列表不会让底层停止给J5–J7发包。
3. `on_activate()` 会 `set_callback_mode_all`、`enable_all`，然后 `return_to_zero()`；回零函数先发一次全0目标，随后200步×10ms插值到0。当前机器人不能原样activate。激活应先以有效新鲜反馈同步命令，再按明确请求执行动作。
4. 默认控制配置update_rate=750Hz，轨迹 `interpolation_method: none`、允许部分关节目标为false，多项轨迹/目标容差配置为0；这些是源码默认值，不能照搬到当前DMMC02链路，也不是实测本机750Hz。
5. 夹爪position映射源码标注近似/未实现真映射，其velocity/effort反馈直接设0。MoveIt2和硬件桥文档也明确处于开发中；不同launch/config中的夹爪action类型需对应核对。

本节源码：[硬编码轴数/型号/ID/增益](https://github.com/enactic/openarm_ros2/blob/8f23aeabb372c256f7807b9a74d48e035fc68386/openarm_hardware/include/openarm_hardware/openarm_simple_hardware.hpp)、[OpenArmHW 实现](https://github.com/enactic/openarm_ros2/blob/8f23aeabb372c256f7807b9a74d48e035fc68386/openarm_hardware/src/openarm_simple_hardware.cpp)、[整臂控制器配置](https://github.com/enactic/openarm_ros2/blob/8f23aeabb372c256f7807b9a74d48e035fc68386/openarm_bringup/config/controllers/openarm_bimanual_controllers.yaml)、[官方 ROS2 控制文档](https://github.com/enactic/openarm/blob/a0c8efb0a9792e34814c18fc805298982d1a9f33/website/docs/api-reference/ros2/control.mdx)；MoveIt入口：[MoveIt demo launch](https://github.com/enactic/openarm_ros2/blob/8f23aeabb372c256f7807b9a74d48e035fc68386/openarm_bimanual_moveit_config/launch/demo.launch.py)、[MoveIt KDL IK](https://github.com/enactic/openarm_ros2/blob/8f23aeabb372c256f7807b9a74d48e035fc68386/openarm_bimanual_moveit_config/config/openarm_v2.0/kinematics.yaml)。

## 重力补偿确实存在，但要按正确方式复用

[gravity_comp 与遥操作可执行构建](https://github.com/enactic/openarm_teleop/blob/eb2d49338bf70ace95282ea724903849397b7811/CMakeLists.txt) 构建 `gravity_comp`。[独立 gravity_comp 主循环（原文件名拼写）](https://github.com/enactic/openarm_teleop/blob/eb2d49338bf70ace95282ea724903849397b7811/control/gravity_compasation.cpp) 主循环读真实motor position，调用 `Dynamics::GetGravity`，将输出组装为 `MITParam{0,0,0,0,t}` 后发到整臂；[Orocos KDL 动力学实现](https://github.com/enactic/openarm_teleop/blob/eb2d49338bf70ace95282ea724903849397b7811/src/controller/dynamics.cpp) 从URDF解析KDL chain，建立 `ChainDynParam(chain, Vector(0,0,-9.81))` 并实际调用 `JntToGravity`。不是只有文档公式，也不是Pinocchio。此处同时有 `JntToCoriolis`、`JntToMass`、Jacobian和FK实现；不能据此夸成现成的全逆动力学辨识套件。

[重力/摩擦/单双向控制](https://github.com/enactic/openarm_teleop/blob/eb2d49338bf70ace95282ea724903849397b7811/src/controller/control.cpp) 把重力、tanh摩擦与部分Coriolis项用于遥操作；摩擦系数来自配置，不是自动识别。[恒等电机/关节映射](https://github.com/enactic/openarm_teleop/blob/eb2d49338bf70ace95282ea724903849397b7811/src/openarm_port/joint_mapper.cpp) 当前只是逐项复制，不能处理本机方向和零偏。官方 nominal 惯性参数见 [官方 nominal 惯性参数](https://github.com/enactic/openarm_description/blob/10ca9bf2f49ef93a2f0f83f97ed2c0fb42dd9a90/assets/robot/openarm_v2.0/config/arm/inertials/nominal.yaml)，适用于官方机械结构，不能当本机真值。

独立 `gravity_comp` 自己创建OpenArm并使能电机（[teleop 初始化与 enable_all](https://github.com/enactic/openarm_teleop/blob/eb2d49338bf70ace95282ea724903849397b7811/src/openarm_port/openarm_init.cpp)），ROS2插件也独占整臂写入路径；不能同时启动两者争写同一总线。正确集成是在统一controller/update周期复用KDL计算并合成tau前馈，底层始终只由一个硬件owner发包。J5仍不可控，但其真实机械姿态及末端负载仍影响J1–J4重力；模型不能简单删除其质量，须固定到已知姿态或建立等效负载。

## DMMC02 与可复用的最小传输边界

[Linux CANSocket 实现](https://github.com/enactic/openarm_can/blob/f3ca25bbda1e239f4cc81f4563fbc75538fef874/src/openarm/canbus/can_socket.cpp) 直接包含Linux网络/SocketCAN头并 `socket(PF_CAN, SOCK_RAW, CAN_RAW)`，通过网卡名取得ifindex；本次已查官方仓没有Windows DMMC02 COM口后端。USB-CAN描述的是设备用途，不保证兼容SocketCAN。未核实DMMC02支持SLCAN协议，所以不能推荐直接执行slcand，也不能把串口帧当裸CAN帧。

优先保留现有DMMC02，将 `send(can_id,payload)` / 接收 `(can_id,payload,timestamp)` 作为适配边界。官方 [CANPacket/MITParam/StateResult](https://github.com/enactic/openarm_can/blob/f3ca25bbda1e239f4cc81f4563fbc75538fef874/include/openarm/damiao_motor/dm_motor_control.hpp) 已有不依赖具体bus实例的 `CANPacket{send_can_id,data}`、`CanPacketEncoder`/`CanPacketDecoder` 和 `MITParam`，可复用编解码；但该头仍include `<linux/can.h>`，Windows编译需解耦Linux头，`DMCANDevice`/socket组件也不是现成可注入的跨平台接口。必要改动是传输封装和设备调度接线，不是重写整套运动控制。当前DMMC02串口协议须沿用本机已验证实现，按收到的CAN ID分发并做新鲜度/错误检查；本次未查询其厂商协议，兼容性判断限于官方后端与本机串口形态差异。

## 增益、状态与力矩语义

[电机编解码实现](https://github.com/enactic/openarm_can/blob/f3ca25bbda1e239f4cc81f4563fbc75538fef874/src/openarm/damiao_motor/dm_motor_control.cpp) 的MIT实际打包范围为kp 0–500（12bit）、kd 0–5（12bit）、q 16bit、dq/tau各12bit；q/dq/tau范围按电机MotorType查表并clamp。必须匹配本机真实型号/固件量程，不能复用官方7轴型号配置猜测。[电机反馈 getter](https://github.com/enactic/openarm_can/blob/f3ca25bbda1e239f4cc81f4563fbc75538fef874/include/openarm/damiao_motor/dm_motor.hpp) 暴露position、velocity、torque、MOS/rotor温度和error code；decoder按CAN payload解析反馈，torque不是外置关节力矩传感器读数。对本机应称“驱动反馈力矩/估计值”，其物理准确度、减速比与标定需另证实；不能据此承诺可直接测得末端接触力。ROS2插件只导出q/dq/effort，没有转发温度/错误状态接口。

## 新版 Dora 链路不是旧 teleop 的别名

较新官方采集链路为 `KER/VR/WebXR →（必要时MuJoCo+mink差分IK）→ Dora arm node → openarm_driver → openarm_can`；另一条可用 [Dora→ROS2 实际桥接](https://github.com/enactic/dora-openarm-ros2/blob/8eb366369d33f9d420b3d10c3af021ca781c308a/src/dora_ros2_bridge/main.py) 把关节目标发布给ROS2轨迹控制器。[实际 UI/leader/robot/recorder 数据流](https://github.com/enactic/dora-openarm-data-collection/blob/e895c2e12488033f30907dafed0ca332e97974c2/dataflow.yaml) 真正接入UI、机器人、采集recorder和250Hz名义leader tick；[实际从臂节点接线](https://github.com/enactic/dora-openarm-data-collection/blob/e895c2e12488033f30907dafed0ca332e97974c2/modules/robot-pedestal.yaml) 把从臂交给 `dora-openarm`。不要把Dora arm driver和ROS2硬件同时接到同一总线；使用ROS桥时应仅让ROS2 owner驱动。

[Python SingleArmDriver runtime](https://github.com/enactic/openarm_driver/blob/5c73d835b31875057695f1b8688e0bf9c0bf87b0/src/openarm_driver/driver.py) 的 `send_position()` 实际MIT命令 `dq=0,tau=0`，带offset和配置kp/kd，因此新版Python driver的常规位置接口本身未做重力前馈。[新控制库职责与动力学边界](https://github.com/enactic/openarm_control/blob/f587a5d0ec7ea4e1c05f2b7d93ee19eb783a796b/README.md) 明说kinetic-energy regularization不是inverse dynamics或gravity compensation。[Dora IK 节点 runtime](https://github.com/enactic/dora-openarm-kinematics/blob/e40dd559d07e3defdc438f459b636a87ddd39684/src/dora_openarm_kinematics/ik.py) 为Dora IK入口，不能把IK、规划和动力学补偿混作同一功能。[driver 限位与停机行为说明](https://github.com/enactic/openarm_driver/blob/5c73d835b31875057695f1b8688e0bf9c0bf87b0/README.md) 明确command成功dispatch不等于已到达、health诊断为observational，且没有fresh-feedback startup gate。

## 建议的复用落地顺序

1. 锁定上游来源；把官方真实HW生命周期/标准控制器架构接到当前工程，创建仅J1–J4的配置与单一总线owner，先替换fake反馈，不从单轴脚本继续堆功能。
2. 将已验证DMMC02收发接在CANPacket边界；建立方向/零偏/量程、有效反馈与可观测故障状态。禁止隐式回零；J5不进入任何enable/command遍历。
3. 用标准JointTrajectoryController验收4轴关节轨迹；模型与限位正确后接MoveIt的4轴任务。不要要求4轴完成任意位置+姿态6自由度目标。
4. 从官方KDL模块复用g(q)计算，先离线核对符号、姿态、参数和负载，再集成统一力矩前馈周期。参数未知时记录为缺口；不以“有重力代码”声称“本机已补偿”。
5. 根据实际示教方式再接Dora/ROS桥与记录器；拖动示教、轨迹重放及具体UI均须独立验收。

本报告没有修改实现或连接硬件；完整运行兼容性、实时性能、DMMC02厂商协议以及自动动力学辨识仍未在本次静态核查中验证。


## 关键补核：本机共享反馈 CAN ID=0 的路由

本机J1–J4当前发送ID为1–4、反馈CAN ID均为0，靠payload首字节低4位motor ID分轴（此本机事实由主任务本地审计提供，未读写电机参数）。官方 [CANDeviceCollection](https://github.com/enactic/openarm_can/blob/f3ca25bbda1e239f4cc81f4563fbc75538fef874/src/openarm/canbus/can_device_collection.cpp) `add_device()` 以 `get_recv_can_id()` 写 `devices_[device_id]`，接收则 `devices_.find(frame.can_id)`；把4个设备都配置recvID=0会覆盖同一map键，不能正确分轴。官方decoder也明确payload低4位不用于路由，因为不能表示15以上ID。

因此除了DMMC02串口传输，还必须保留/适配本机payload分轴逻辑，不能声称只改几个CAN ID配置即可。适配应在统一owner内：先确认帧格式、长度与反馈类型，再在本机已验证ID1–4范围内按payload motor ID分发，更新各轴独立时间戳/故障状态；J5不进入控制注册集合。不同参数回复帧不能未经分类就套同一低4位规则。本任务保持现有电机master ID、零位、模式等参数；不能为迎合上游map结构擅自写电机参数。

此外 [DMDeviceCollection构造/发送实现](https://github.com/enactic/openarm_can/blob/f3ca25bbda1e239f4cc81f4563fbc75538fef874/src/openarm/damiao_motor/dm_motor_device_collection.cpp) 和 [声明](https://github.com/enactic/openarm_can/blob/f3ca25bbda1e239f4cc81f4563fbc75538fef874/include/openarm/damiao_motor/dm_motor_device_collection.hpp) 具体依赖 `CANSocket&` 并直接调用CAN/CAN-FD写入，所以transport seam需要有边界的fork/adapter重构，当前不是上游现成可注入接口。复用层次为协议编解码、模型计算、ROS标准控制器与架构；传输和路由适配是必须交付的真实工作。
