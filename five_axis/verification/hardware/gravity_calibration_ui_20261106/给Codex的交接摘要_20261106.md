## 7. 双机遥操与“一键切换”想法（SLAI + 松灵）

### 7.1 先把问题问清楚（建议向 leader 确认）

1. “遥操”具体指哪种：
   - 松灵主臂带动 SLAI 从臂（主从遥操作）？
   - 还是用同一个操作端（手柄/VR/主臂）分别遥操两台臂？
2. “在松灵上位机里实现”是硬性要求，还是允许松灵上位机只做显示/切换、控制由旁路网关负责？
3. 一键切换的目标：只切换**当前被遥操的从臂**，还是连主臂/操作端也一起切？
4. 两台臂是否同时上电/联网？各自谁持有串口/CAN/网络？是否共享硬件急停？
5. SLAI 只有 4 轴，松灵主臂通常 6/7 轴：关节映射、IK、工作空间、离合器/缩放策略如何定？
6. 切换是否允许在运动中进行？（强烈建议只允许停稳/失能后切换。）

### 7.2 建议架构（与厂商上位机解耦）

分四层，核心是“**同一时刻只有一个臂是活动所有者**”：

1. **设备适配层（Arm Adapter）**：每个臂实现统一接口
   `connect/disconnect`、`state`、`enable/disable`、`mode`、`command`、`stop`、`identity`、`limits`、`status/audit`、`capabilities`。
   - SLAI 适配器复用现有受保护客户端、会话租约、停止纪元、身份/限位/审计；
   - 松灵适配器封装其 SDK/ROS 驱动/远程 API。
2. **会话仲裁层（Session Arbiter）**：
   - 一次性“活动臂”租约；切换必须走状态机：停止当前遥操 → 确认停稳/失能 → 释放串口/CAN/网络 → 校验新臂身份/配置/限位 → 激活新臂 → 才允许遥操；
   - 运动/使能中禁止切换；全轴停止优先级最高；任何异常/断连默认回安全态；
   - 同一时刻禁止两臂同时接收遥操命令。
3. **遥操提供层（Teleop Provider）**：
   - 与臂无关：输入源（主臂/手柄/VR/滑条）、离合器、缩放、死区、滤波、速度/加速度限幅、工作空间映射；
   - SLAI 的“手拖重力补偿”可作为其中一种输入/模式；主从遥操另做映射与 IK。
4. **UI 层（松灵上位机）**：
   - 一个“活动臂”选择器/一键切换按钮；显示当前臂身份、模式、限位、安全状态、停止/急停；
   - 每台臂独立参数页（重力模型、限位、Kp/Kd、遥操映射、速度上限）；切换按钮只在安全态可用。

### 7.3 两条实现路径

- **路径 A（松灵上位机开放插件/节点）**：在其插件/脚本层实现上述四层；我们提供 SLAI 适配器和切换仲裁接口。
- **路径 B（上位机封闭）**：做一个旁路“双机遥操网关”（ROS2 或 WebSocket/ZeroMQ 服务），网关同时持有两臂连接并强制单一所有者；松灵上位机只调用网关的 `select_arm/teleop/stop` 接口做显示与一键切换。这样不用改厂商内部代码，风险最低。

### 7.4 安全不变量（必须写进接口）

- 单臂单一控制所有者；切换前旧臂必须停止并确认失能；
- 全轴停止/硬件急停独立于软件，任何模式都能立即生效；
- 切换/断连/超时/心跳丢失 → 默认失能，不自动续跑；
- 每台臂独立加载身份、限位、重力模型，禁止跨臂复用；
- 遥操命令限幅/滤波在网关侧完成，不依赖上位机 UI；
- 全程 audit：谁、何时、切换了哪台臂、执行了什么模式。

### 7.5 建议 MVP 顺序

1. 等 leader 发松灵资料后，先确认其 SDK/上位机扩展方式与通信协议；
2. 定义统一 `ArmAdapter` 与 `select_arm` 接口 + 单所有者状态机（先用两个假臂/仿真验证切换与互锁）；
3. 接松灵（只读/失能状态）→ 接 SLAI（沿用现有），做一键切换的“只切换、不运动” MVP；
4. 再实现单臂遥操（先在 SLAI 上，用现有拖动/位置保持作为基线），最后做主从映射；
5. 实机验收按“单臂静止切换 → 单臂低速遥操 → 双臂交替 → 异常/急停”分阶段，任一步不通过不进入下一步。

### 7.6 需要 leader 提供的文件/信息

- 松灵臂型号、SDK/ROS 驱动/上位机架构说明、通信协议、控制接口、状态/错误码；
- 松灵上位机是否允许插件或外部进程、是否有远程 API；
- 两台臂的供电/急停/网络拓扑、串口/CAN 归属；
- 遥操需求：主从关系、轴映射、工作空间、速度/力限制、切换场景与验收标准。
